# ADR-0025: Learning Across Investigations

- Status: Accepted
- Date: 2026-09-18

## Context

Lab 3 v2 retains lessons only after complete passing fixes and builds its two
initial chain supports from two excerpts of one investigation. Its notebook receives
the same procedure as MindLeak. This tests provenance and delivery, not independent
principle formation or useful findings retained from unfinished work.

## Decision

Add an explicit v4 `mechanism` profile, initially leaving existing v2/v3 fixtures, defaults,
reports and scoring intact. PR #41 already owns multi-principle protocol v3 and
the live learning frontend. Preserve its CSS, stage, graph, motion, controls and
default Learning profile; add investigation evidence below that stage. The initial
provisional-v3 investigation report remains historical, never relabeled.
Keep the three MCP tools/tables and current explicit knowledge
lifecycle. New orchestration belongs in the example lab, not the MCP service.

- Capture source observations only from complete executed probe receipts and exact
  inspected quotations. Overall task success is a separate field. Failed checks
  support observations; they do not automatically establish a causal explanation.
- Treat each discovery case as one evidence origin. For this bounded experiment,
  two different constructed cases and source groups must support two accepted
  chains before a principle can be proposed. IDs alone are not independent proof.
- Freeze the proposed procedure before reserved validation. Record predictions
  before execution, preserve boundary failures, and require explicit acceptance.
  A correctly handled boundary is allowed; do not force every valid procedure to fail.
- Give notebook and MindLeak authors the same discovery evidence, model, budgets,
  and validation opportunities. Notebook notes are independently authored, not
  copied principles or deliberately poor summaries.
- Match 12 evaluation sessions across fresh, notebook and MindLeak arms on four
  new cases. Keep four direct-delivery diagnostics separate. Retrieval is optional;
  record all misses, non-use, failures and scheduled denominators.
- Keep shared knowledge frozen during comparison. Post-comparison reviewers see
  only their own arm's outcomes, can retain actual exceptions, and can propose
  revisions. Exposed validation cases cannot accept a changed hypothesis.
- Report checked discoveries, prospective predictions, pre-edit decisions and
  conditional later use separately from complete task success and full costs.
  Keep unavailable semantics, billing and general-benefit claims unmeasured.

### Main Reuse Workflow

The subsequent v3 Learning run formed knowledge but its evaluation agents never
consulted it. Optional adoption and the normal reuse workflow answer different
questions. New Smoke, Learning and Pilot runs therefore use **v5 knowledge-first**;
the v3 policy remains an explicit `adoption` diagnostic. Frozen fixtures, checks,
historical reports and the separate v4 mechanism are unchanged.

MindLeak and notebook evaluation agents must perform an actual lookup and record
a source-linked applicability decision before editing. They may apply, adapt or
reject delivered knowledge, or continue locally after a recorded miss/error. The
fresh baseline stays unchanged. Only an applied/adapted delivered lesson preceding
a changed passing candidate earns v5 application credit; lookup or a declaration
alone cannot. The assessment is attributed evidence, not independent semantic
validation. Existing costs, failures and all scheduled denominators remain.

Workflow revision 2 starts both experience arms with the task subject already
available to all arms and explains active keyword AND semantics. This follows an
actual recorded miss; the earlier workflow check is preserved with its module
hashes and is not relabelled. The lab never changes retrieval modes or scores to
obtain a hit. Formation, lookup, assessment and application have separate counters.

### Verified Component Sharing

Lab 1's optional-use v2 policy likewise allowed a successful build without
publishing or consuming component findings. New memory-team runs use
`verified-handoff-v3`: complete component checks precede a source-qualified MCP
write, and every dependency's current original handoff must be received before
editing. Supplied source IDs are pointers, not delivered knowledge. A failed
write, a partial set of dependencies, a search excerpt or an older run's finding
cannot satisfy this contract. Editing after publication invalidates the current
handoff while preserving its source history.

Code checks and collaboration completion are separate measurements. The memory
team needs both; the no-memory controls retain their unchanged code-only contract.
Continued comparison reports preserve inherited findings alongside new writes.
The guided demonstration proves actual source transfer, not independent truth,
novelty, automatic adoption or a causal performance advantage. The MCP API,
fixtures and old recordings are unchanged.

### Shared Knowledge-First Startup

Lab 1 v3's pointer handoffs did not require a search for related prior art. New
`knowledge-first-handoff-v4` coding sessions require their own scoped search,
original-source inspection and applicability assessment against an inspected
current-file quotation before editing. Genuine misses/errors permit explicitly
assessed local work. Required dependency handoffs and verified writes still apply.

The companion skill v1.5.0 and both model adapters make this the startup policy
whenever approved tools support the configured scope. Explicit independent
discovery, optional-adoption diagnostics and no-memory controls retain their
declared boundaries. This changes client workflow, not MCP permissions or recall
side effects. No new tool, worker, table or implicit knowledge acceptance is added.

Lab 2 v6 gates downstream probes/assessments on prior lookup and original source
inspection. Its read-only evaluation gate preserves control isolation and genuine
miss/error outcomes. Pending guide candidates expose exact acceptance actions;
unaccepted candidates remain incomplete rather than being relabelled as learning.
Live use accounting requires a matching earlier application receipt and a passing
assessment; missing measurement remains unknown. Source-linked application,
formation and comparative benefit remain separate claims.

### Source-Checked Handoffs

The v4 run checked memory at startup but accepted an applicability quote from
the consumer's own unimplemented stub. Its integration note then claimed it had
matched dependency files that its trace never read. New Lab 1 v5 handoffs pin
the published module hashes and require actual matching dependency-file reads
before edits and publication. Apply/adapt claims for current handoffs cite those
module paths. Changed files, even when reread, require a current publication.
Reports keep these checks separate from source delivery and semantic validation.

The fixture's existing active/expired view checks now assert the documented
nonempty status badge. Both arms receive the same stricter fixture. Its new hash
distinguishes it from historical runs whose checks omitted that requirement;
old outcomes and generated artifacts remain unchanged.

### Bounded Guide Decisions

Lab 2 run `70de06f6-bd8f-4dae-8cf4-da8aa2c299ab` applied its stored procedure
correctly but the subsequent guide sessions only reread knowledge. A first
one-dossier prototype still allowed the model to stall on checkpoints. Protocol
v7 therefore makes evidence preparation and decision distinct phases rather than
adding retry counts or stronger encouragement to the same unrestricted loop.

The example runner retrieves one bounded dossier through existing MCP operations:
current documents, exact original observation sources, verified current assessment
and pending acceptance IDs. It preserves all cited evidence and fails over 64 KiB
instead of silently truncating the review. The guide model receives that untrusted
context with only proposal/revision, explicit acceptance and no-new-learning tools.
There is no read/checkpoint loop, automatic acceptance or mandatory new principle.
Pending candidates must be resolved before new proposals. Changed catalogue state
invalidates a review; only current review-ready principles can justify a skip.

Completion still requires actual successful operations and the resulting checkpoint,
not a claimed final answer. Model turn/time/credit limits and bounded idle handling
are unchanged. Source preparation costs remain measured. The same orchestration
serves initial and between-round guide authoring; core extraction and the frozen
read-only comparison contract do not change. Historical failed runs remain intact.

### Explicit Principle Application

The full v7 run `93d41bbc-f28d-4f11-8958-e792d613296a` completed guide synthesis,
but Vega's initial keyword search returned case chains rather than a principle.
Its technical assessment was allowed to pass and froze an empty eligible-guide
set. Later principle retrieval could not truthfully establish prior use. A generic
binding error also failed to distinguish case-chain IDs from reusable principles.

Protocol v8 requires an actually delivered review-ready principle before downstream
preparation probes/assessment. Search and inspection expose exact typed application
references; catalogue pointers can guide an explicit scoped inspection after a
chain-only hit but are never credited as delivery. The first passing assessment
freezes eligible principle IDs/revisions, returned again by its checkpoint.
Applications reject wrong-kind references, revision mismatch, changed review state
and retrospective retrieval. Existing original-source and exact-quotation checks
remain. No retrieval query, score, filter, core tool or stored history is changed.

### Bounded Lab 3 Case Reviews

The five-family Learning study `881c1dbe-71d2-4b31-b34c-cbfd8a18f52a`
passed all 135 coding checks but completed none of its three reviews. Its separate
Lab 3 reviewer retained search/inspection tools, so the Lab 2 guide fix did not
control that path. A final completion flag also did not require a review decision.

The initial case reviewer recorded `plan.reviewPolicy` version 1 independently of the
unchanged v5 coding workflow, fixture hashes, schedules and scoring. Prepare one
untrusted source packet with verified memory-side cases, current principles and
support, original observations checked through MCP, applicability decisions and
retention failures. Fail the complete packet above 128 KiB; do not truncate away
conditions or counterevidence. Controls and future cases never enter this review.

The model then has only `retain_lesson` and source-linked `skip_learning`. Completion
requires an explicit successful decision for every verified case, no unresolved
persistence attempt and a successful final answer. Keep the ten-attempt retention
bound and existing model budgets; there is no new-lesson quota or automatic retry.
Correct rejection is useful evidence distinct from application. Exact-proposal
retry receipts can resolve uncertain writes; unrelated successes and skips cannot.
Pre-write validation rejection can be corrected without hiding its error history.

The source-backed decision loop and successful retention are separate requirements.
The initial three-review rehearsal failed all three provider retention requests at
240 seconds, but subsequent investigation found it omitted the live lab's explicit
reasoning setting. Preserve that mismatched result instead of attributing its
failure to the unchanged live configuration. Report reasoning controls alongside
other runtime settings so this difference cannot be hidden by configuration equality.

Review-policy v2 separates side-effect-free authoring from persistence. The model
returns a complete bounded JSON decision document without tools. The runner checks
the full case set and all source quotations before executing explicit retention
choices. This follows repeated pre-handler SDK query failures in batched-tool
prototypes; changing object keys to an array did not resolve them. The design removes
that dispatch dependency rather than claiming the SDK itself was repaired.

Malformed, partial, unfinished or cancelled documents cannot start writes. Every
requested proposal must receive a successful receipt; a successful sibling proposal
does not conceal failure. Authoring and persistence share one deadline through an
MCP cancellation signal, preserving earlier acknowledged writes. No repair loop,
model substitution or extra retry is added. Shared adapter validation reports only
bounded schema paths and constraint codes, not private output. The original core
and operator hold remain intact.

## Consequences

A failed or unfinished task can produce durable, auditable evidence without
being called a successful task. Principles must earn experimental support instead
of gaining it from extra records. The first profile is one synthetic family and
cannot establish population generalization or a causal productivity advantage.
The server checks attributed records and provenance, not model reasoning truth.

Preparation and validation add cost. Both experience arms receive the same offered
budgets; actual run totals and counterfactual allocations remain separate.
Rejected candidates and no-new-learning outcomes stay visible. Existing recorded
studies are not rewritten, and v4 initially refuses continuation until fresh-case
allocation can be guaranteed.

## Verification

- Unit regressions cover disjoint plans, exact receipts, partial discoveries,
  distinct-case support, frozen predictions, explicit acceptance, and fresh
  validation requirements after challenge/revision.
- Real MCP and container checks execute both discovery paths, reserved positive and
  boundary checks, twelve main evaluations, four diagnostics and retained exceptions.
- Main-workflow regressions block edits before lookup/assessment, preserve valid
  misses, errors and rejections, and check both real MCP and notebook paths.
- Lab 1 regressions require all current dependency sources and acknowledged
  verified publications, reject stale/failed handoffs, preserve inherited source
  history and keep no-memory controls isolated. Live counters and code correctness
  remain separate from sharing completion.
- Shared startup regressions reject edits without per-session search and
  assessment, invented/delivered-only source IDs, unread current evidence, and
  mismatched miss/error claims. Lab 2 covers pre-assessment gating, explicit
  pending acceptance, live application receipts and unchanged control access.
- Source-checked handoff regressions reject unread or changed dependency files
  and unrelated stub evidence. Sandbox view tests reject missing and empty status
  badges and accept nonempty badges in both states.
- Synthesis tests cover one-time original-source delivery, no read tools in the
  decision phase, explicit no-new-learning completion, pending acceptance, stale
  revisions, challenged principles, oversized evidence, cancellation and truthful
  failure/usage accounting. The real MCP relay covers both preparation and review.
- Guide-application tests reproduce case-chain-only lookup, explicit principle
  inspection before verification, exact ID/revision recovery, and rejection of
  supporting-chain IDs, stale review state and post-assessment retrieval.
- Lab 3 review regressions cover decision-only tools, exact current-source skips,
  partial case coverage, stale or oversized packets, original-source mismatch,
  duplicate/control IDs, failed-write attribution and exact-proposal recovery.
  The real MCP smoke and continuation tests preserve frozen comparison and cost
  accounting; the failed real-provider rehearsal remains separate evidence.
- Review v2 tests require full-document validation before side effects, distinguish
  author completion from persistence, retain successful partial receipts, reject
  duplicate/unknown case IDs and enforce the existing deadline. Shared adapter
  tests cover private-safe validation diagnostics and query-dispatch errors without
  retries. Failed prototypes and concurrent source-hash guards remain in the record.
- Existing lab/profile, replay, privacy and contract boundaries remain covered;
  `make ci` runs against a disposable `_test` database.
- Desktop/mobile browser checks cover the versioned profile and evidence view.
  Real model runs, if performed, remain separate evidence from deterministic tests.
